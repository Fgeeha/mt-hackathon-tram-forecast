# План реализации: прогноз загрузки трамвайных маршрутов

Трек 2 хакатона Московского транспорта (https://mt-hackathon.ru/).
Стек: всё на Python. Данные приходят **25.09 после 10:00** — до этого
готовим всё, что не зависит от их точной схемы.

## 1. Что сдаём

1. Модель прогноза пассажиропотока на три горизонта: 1 день, 1 месяц, 1 год.
2. Агрегация прогноза по маршруту, остановке и временному интервалу.
3. Веб-сервис: карта Москвы с загрузкой остановок/перегонов, фильтры,
   графики, режим «сейчас» (проигрывание последних суток).
4. Отчёт по качеству: бэктест против наивных бейзлайнов.

## 2. Архитектура

```
raw (csv/parquet от организаторов)
  └─ adapters/        приведение к канонической схеме (единственное место,
                      которое зависит от формата организаторов)
       └─ data/canonical/*.parquet
            └─ aggregate  → stop_hour.parquet (маршрут × остановка × час)
                 └─ features → train → models/{day,month,year}.lgb
                      └─ forecast → forecasts.parquet
                           └─ FastAPI  ── /api/*  +  статический фронт (MapLibre)
```

- Хранилище: parquet + DuckDB (SQL-агрегации миллионов строк без сервера БД).
- Обработка: polars/duckdb, модели: LightGBM, API: FastAPI + uvicorn.
- Фронт: одна HTML-страница, MapLibre GL + ECharts, раздаётся тем же FastAPI.
- Прогнозы считаются заранее (batch) и отдаются из parquet — API не держит
  модель в горячем пути, отвечает быстро.

## 3. Каноническая схема (под неё пишется адаптер)

| Таблица | Поля |
|---|---|
| `validations` | `ts`, `route_id`, `stop_id?`, `vehicle_id?`, `card_id?`, `ticket_type?` |
| `telematics` | `ts`, `vehicle_id`, `route_id?`, `lat`, `lon` |
| `stops` | `stop_id`, `name`, `lat`, `lon` |
| `route_stops` | `route_id`, `direction`, `seq`, `stop_id` |

`?` означает, что поле может отсутствовать. Если в валидациях нет `stop_id`,
остановку восстанавливаем так: `vehicle_id + ts` → ближайшая точка
телематики → ближайшая остановка маршрута (`merge_asof` по времени, затем
поиск ближайшей остановки через KD-tree).

## 5. Целевая переменная

- **MVP:** `boardings` — число входов на (маршрут, остановка, час).
  Надёжно считается из валидаций при любой схеме.
- **Загрузка перегонов (stretch):** `load(segment) = Σ входов − Σ выходов` вдоль
  рейса.
  - есть `card_id`: выходы оцениваем по цепочкам поездок (trip chaining):
    выход — ближайшая к следующей валидации карты остановка, для последней
    поездки дня — остановка первой поездки;
  - нет `card_id`: выходы распределяем по остановкам пропорционально их
    историческим входам в обратном направлении (приближение гравитационной
    модели).
- Безбилетников и льготников без валидаций не видим — в отчёте указываем, что
  прогноз строится по валидациям, коэффициент досчёта можно ввести отдельно.

## 6. Модели

Одна схема — LightGBM, глобальная модель на все ряды, **прямая стратегия
по горизонту**: у каждого горизонта свой набор лагов, которые ещё известны
на момент прогноза.

| Горизонт | Лаги | Признаки | Бейзлайн |
|---|---|---|---|
| 1 день | 1д, 7д, 14д, rolling 7д/28д | час, день недели, праздник, погода* | то же время неделю назад |
| 1 месяц | ≥35д (5 нед), rolling 28д | + месяц, школьные каникулы | среднее за те же день недели/час за 4 нед |
| 1 год | ≥364д | + тренд маршрута (год к году), месяц | тот же день недели/час год назад × тренд |

Общие категориальные признаки: `route_id`, `stop_id`, направление.
*Погода — только если останется время (Open-Meteo archive, бесплатно).
Для года дополнительно поправка на известные изменения сети (новый/закрытый
маршрут) — вручную, если будут данные.

**Валидация:** rolling-origin бэктест по времени (без перемешивания),
минимум 3 окна на горизонт. **Метрики:** WAPE (главная, понятна диспетчеру),
MAE, отдельно по часам пик. Результат — таблица «модель vs бейзлайн».

## 7. API

| Метод | Назначение |
|---|---|
| `GET /api/routes` | маршруты + геометрия (GeoJSON) |
| `GET /api/stops?route_id=` | остановки |
| `GET /api/forecast?horizon=day\|month\|year&route_id=&stop_id=&from=&to=&agg=hour\|day` | прогноз с агрегацией |
| `GET /api/load/map?horizon=&ts=` | снимок загрузки всех остановок на момент времени (для карты) |
| `GET /api/metrics` | качество моделей по бэктесту |

## 8. Интерфейс

- Карта Москвы: остановки — кружки, цвет/размер по загрузке; перегоны — линии
  маршрута с толщиной по загрузке (если успеем stretch).
- Панель: выбор горизонта, маршрута, остановки, диапазона дат/часов.
- Ползунок времени + кнопка «проиграть» — «реальное время» на исторических сутках.
- Клик по остановке → график: факт, прогноз, бейзлайн.
- Вкладка «Качество» — таблица метрик.

## 11. Риски

| Риск | Что делаем |
|---|---|
| Нет привязки валидаций к остановке | Восстановление через телематику (п. 3) |
| Нет `card_id` | Загрузку перегонов считаем по упрощённой модели, основной результат — входы |
| Данных < 2 лет | Годовой горизонт: сезонный профиль + тренд, честно пишем об ограничении |
| Объём не лезет в память | DuckDB вместо polars, агрегация до часа сразу при чтении |
| Не успеваем stretch | MVP (входы по остановкам) закрывает все обязательные пункты задания |
